# Web UI plugin

The familiar web interface: a React app built with [shadcn/ui](https://ui.shadcn.com/), Tailwind CSS v4 and Vite. It is meant to be bundled (always on). Until its first npm release it is `private` and not yet `familiar.bundled`, so enable it by adding `@getfamiliar/plugin-web-ui` to `config/plugins`. It needs `webserver.enabled: true` and at least one login in `webserver.auth.users` (see [`docs/config.md`](../../docs/config.md#webserver)).

The plugin does no authentication. Its `webUi` hook returns the root controller, which the core webserver mounts at `/` behind its auth middleware, so every request it sees comes from a signed-in, allowlisted user (`c.get("principal")`). Login and logout (`/login`, `POST /logout`) stay core routes.

## Login pages

The core webserver lets this plugin render the login pages, but not run them: it decides which page to show (signed in, not signed in, confirm a login link, link not valid), with which status code and form actions, and passes that as a `WebAuthPageView` to `renderAuthPage`. Redeeming a link and signing out remain core code.

The pages use the look of the shadcn block `login-04` (`src/components/auth-page.tsx`) and are rendered on the server to static HTML (`src/ssr/render-auth-page.tsx`). They are reachable without a session and are served under a strict Content-Security-Policy: no scripts, no external resources. So the page carries everything itself: the CSS is inlined, the fonts as `data:` URIs (in the production build), and every action is a plain link or form. That's why a page is about 180 kB.

## Layout

```
plugins/web-ui/
  index.html  vite.config.ts  components.json   # Vite entry, Vite config, shadcn config
  biome.json                                    # nested Biome config: skips src/components/ui
  tsconfig.app.json   # client (src/, without src/host), type-check only
  tsconfig.host.json  # host side (src/host → build/index.js)
  src/
    main.tsx  App.tsx  index.css   # app entry, shell, Tailwind + shadcn theme
    components/ui/                 # generated by shadcn — don't edit by hand
    components/                    # our own components (sidebar, nav, …)
    hooks/  lib/                   # React hooks (use-shell, use-mobile), cn helper, menu helpers
    ssr/render-auth-page.tsx       # server-side renderer of the login pages
    host/                          # plugin host side: controller, static assets, login-page bundle, Vite bridge
```

`src/components/ui/` is shadcn's code: regenerate or update it with the shadcn CLI and keep it out of formatting and linting. Our own UI goes into `src/components/`. The sidebar scaffold comes from the `sidebar-07` block (sidebar that collapses to icons); its navigation entries are placeholders.

## Adding shadcn components

Run the CLI in this folder:

```bash
cd plugins/web-ui
npx shadcn@latest add <component>
```

The CLI adds new npm packages to `dependencies`. Move them to `devDependencies`, because everything on the client side is bundled at build time. Only the host side's runtime packages (`hono`, `@hono/node-server`, `@getfamiliar/shared`) are real dependencies.

## API

The controller serves JSON under `/api`. Right now there is only `GET /api/shell`, which returns what the app shell needs: the signed-in user (`user`: `login`, `displayName`, `via`), the familiar `version`, the sidebar `menu` and the plugin `pages`. Unknown `/api/*` routes get a JSON 404. Every other path is served as UI.

## Menu

The sidebar holds no menu items of its own. Every plugin can contribute some through its `webMenu(ctx)` hook ([`docs/plugins/create-plugins.md`](../../docs/plugins/create-plugins.md#web-ui-menu-items)). The core sorts them by plugin weight and the controller passes them on in `/api/shell`. `GET /` redirects to the first route of the menu, and with an empty menu it stays on the start page. Icons are lucide ids, loaded on demand via `DynamicIcon`. Each icon is its own small chunk in `build/client/assets`, and unknown ids show a dot. The menu links are plain links, so each page is a full page load that comes back through the SPA fallback.

## Plugin pages

Routes under `/plugins/<id>` belong to the page of that plugin (its `webPlugin` hook, see [`docs/plugins/create-plugins.md`](../../docs/plugins/create-plugins.md#plugin-pages-and-controllers)). `src/components/plugin-page.tsx` imports the page module and mounts it into the content area. While it loads you see a spinner, and if it fails, an error card. In production that is the plugin's built module. In dev mode, when the plugin names its `sourceFile`, it is the source through this plugin's Vite server.

## Development

In a dev run (`npm run dev -- start`, i.e. `FAMILIAR_DEV=1`) the plugin starts Vite in middleware mode inside the daemon. Pages and modules go through the core webserver and its authentication, so you sign in as usual (`npm run dev -- web login`). Edits to `.tsx` and `.css` files show up immediately through hot module replacement, with no daemon restart.

- The HMR websocket listens separately, on the first free port from `127.0.0.1:24678`, so a second dev instance takes the next one. Live reload therefore works when the UI is opened via `localhost`. Through the tailnet or another proxy the page works, but you have to reload it by hand.
- The login pages are rendered from source via Vite's `ssrLoadModule`. Changes show up on the next page load (they have no script, so there is no HMR). In dev mode their fonts are not inlined and the CSP blocks them, so they render in the fallback font.
- Plugin pages with a `sourceFile` go through this same Vite server, so they get the same hot reload. `vite.config.ts` resolves `@/` per package (`packageSourceAlias`), and `server.fs.deny` keeps `config/`, `data/` and `tmp/` out of `/@fs/`.
- Changes to the host side (`src/host/`) still need a daemon restart.

## Production

`npm run build` type-checks both sides, compiles the host side to `build/`, bundles the client to `build/client`, and bundles the login-page renderer to `build/ssr` (`vite build --ssr`, without external npm dependencies, all assets inlined). The controller serves the bundle from there: hashed files under `/assets/` are cached forever, `index.html` is never cached, and unknown paths without a file extension get `index.html` so client-side routes survive a reload. If `build/client` is missing, the controller answers with a 500 that says to build it.
